# Generalized (Padding) DataWidthConverter — Work Log

Branch: `dev-generalized-dwc` (FINN) + edits to `deps/finn-hlslib/streamtools.h`.
Goal: make the generalized/padding DWC usable inside the folding optimizer for
fine-grain node sizing, and make it LUT-efficient at large widths (≥1024 bit).

## Scope of changes (keep minimal)
- HLS: only `StreamingDataWidthConverterGeneralized_Batch` in `deps/finn-hlslib/streamtools.h`.
- FINN: only `streamingdatawidthconverter.py`, `hls/streamingdatawidthconverter_hls.py`,
  `insert_dwc.py`. Interfaces are fixed unless broken.
- Tests: extend `tests/fpgadataflow/test_fpgadataflow_dwc.py`.

## Interfaces (as designed)
- `StreamingDataWidthConverter` node attrs: `in_shape`, `out_shape`, `inWidth`, `outWidth`, `dataType`.
- Padding/cropping: when `prod(in_shape) != prod(out_shape)` the DWC pads with zeros (out>in)
  or crops (out<in). Element-count in last dim differs.
- `InsertDWC`: picks `rtl` when widths are integer-multiples AND no padding; else `hls`
  (= generalized variant).
- HLS kernel template params: `<InWidth, OutWidth, NumInWords, NumOutWords>(in, out, numReps)`.
  `numReps = prod(folded_in_shape[:-2])`, `NumInWords = folded_in[-2]`, `NumOutWords = folded_out[-2]`.

## Current HLS algorithm (baseline, streamtools.h ~601)
Buffer `eo` of width `InWidth+OutWidth`, `els_in_buffer` tracks valid bits.
Per cycle: if buffer has ≥OutWidth valid bits, write OutWidth out + shift down by OutWidth (const shift, cheap);
if room, read InWidth in at **variable offset** `els_in_buffer` → `eo(InWidth+els_in_buffer-1, els_in_buffer)=ei`.
**This variable-offset write is a barrel shifter of ~(InWidth+OutWidth) bits → the LUT blowup at large widths.**

## Non-multiple optimization (v4, log-depth barrel) — 2026-07-21
The non-multiple path was rewritten from a lane-array (per-lane shift muxes, cost
did not shrink with a bounded placement) to a **single (InWidth+OutWidth)-bit
register**: constant-shift emit (free wiring) + a **log-depth barrel** that places
the new word at bit offset `lanes*G` in `ceil(log2 OutLanes)` conditional
power-of-two constant shifts (units of G=gcd). Cost ~ `bufwidth*log2(OutLanes)`.
Needed a `get_ap_int_max_w` override (buffer is wider than max(in,out)).

| in→out | lane-array | v3 chained-select | v4 barrel | **v5 +BufW** |
|---|---|---|---|---|
| 48→32   | 626  | 475   | 510  | 510  |
| 96→40   | 1808 | 1146  | 892  | **876**  |
| 44→48   | 2418 | 1659  | 747  | **739**  |
| 88→40   | —    | —     | 860  | 860  |
| 480→512 | 3343 | 16508 | 4088 | 4088 |
| 1024→768| —    | 5794  | 5243 | **4731** |

v5 sizes the buffer to InWidth+OutWidth-G (max occupancy = (BufLanes-1) lanes),
shaving the wide large-gcd cases (1024→768). Net vs the original lane-array:
common non-multiples 2–3× smaller (96→40 1808→876, 44→48 2418→739); wide near-1:1
(480→512) comparable. The remaining ceiling is inherent — a ~500–1500-bit
arbitrary-ratio barrel (cost ≈ InWidth·log2(OutLanes) + OR-merge + emit-mux),
near the theoretical floor. Muxing is at G=gcd-lane granularity (never finer than
the transfer unit); the barrel is bounded to OutLanes phases (the only fill
levels a read can see). Ideas tried and rejected: bounded lane-array (no gain),
chained-select (blows up wide), input-side upscale (only helps rare high-ratio),
let-HLS-barrel a variable shift (bit-granular, worse), lane/barrel hybrid
(~20% on one rare case, not worth a second code path).

- **Padding/cropping add zero overhead**: same datapath, only word counts differ
  (44→48 pad = exact = 747; 96→40 crop = exact = 892).
- v3 chained-select won for tiny widths but blew up for wide+high-OutLanes
  (480→512 = 16508, since chained cost ~ OutLanes×bufwidth); the log-barrel fixes
  that (log, not linear, in OutLanes).
- Wide near-1:1 cases (480→512, 1024→768) remain the ceiling — inherent to a
  ~1000–1800-bit arbitrary-ratio barrel; still log-scaling and bounded. Report
  breakdown (1024→768): barrel ~3072 + OR-merge ~1792 + emit-mux ~900 LUT.
- Multiple cases unchanged (separate const-shift branches): 128→64/1024→512 = 263.

## Resource-analysis plot (real Vivado synth) — 2026-07-21
`dwc_resource_analysis.tex` (3 pgfplots, generated by `make_tex.py` from
`plotdata.json`). **Methodology matters:** the optimization sweeps above use Vitis
HLS **csynth estimates**, which *flat-line* for register-dominated datapaths (e.g.
263 "flat" for the multiple case). Real **Vivado OOC synthesis** LUTs *grow* with
width. The plot therefore synthesizes every variant the same way — RTL core via
Vivado; HLS/Generalized via `vitis_hls` csynth → Vivado OOC synth of the emitted
Verilog (`collect_vivado.py`) — so all curves are comparable. Findings (real LUTs):
- Multiple: `gen_mult` ≤ `hls_mult`, both above the compact RTL (no penalty). E.g.
  1024→512: RTL≈518, HLS≈1353, gen≈1318 (plot3); all scale ~linearly with width.
- Non-multiple: `gen_nomult` is **below** the LCM cascade (`hls_nomult`) everywhere,
  and the cascade **fails** at 720→768 (LCM 11520 > 8191) where the generalized keeps
  working. So generalized is both more compact and more robust on non-multiples.
- (The earlier csynth-based flat numbers are estimates, not silicon; treat the
  relative optimization deltas as directional and this plot's Vivado numbers as real.)

## Results log

### Correctness (bit-accurate C-sim, `tb_dwc.cpp`, 40 cases)
Standalone g++ testbench compiles the kernel against Vitis HLS headers and checks
against a bit-vector reference (LSW-first, LSB-first, zero-pad, top-crop). Covers
multiple/non-multiple/coprime widths, padding, cropping, single-word, reps, and
wide words up to 1024 bit. **ALL 40 PASS** on the new kernel.
- Found + fixed a real bug: in **cropping** (output complete before input drained)
  the downscale path stalled reads → leftover input bled into the next rep.
  Fixed by draining/discarding remaining input once `words_written==NumOutWords`
  (both up- and down-scale). This bug pre-existed in the original kernel (untested).

| **non-mult exact** | 48→32 / 96→40 / 44→48 | 626 / 1808 / 2418 | | lane-array |
| **pad** | 8→16 / 4→32 (mult) | 499 / 892 | | lane-array |
| | 44→48 / 480→512 (non-mult) | 2418 / 3343 | | lane-array |

**Key outcomes**
- Multiple-case LUT is **flat at ~156 (upscale) / ~263 (downscale)** across all
  widths AND ratios (was O(W): up to 21969) — **at or below the plain/RTL-equivalent
  reference** (215/292), while additionally supporting padding, cropping and
  arbitrary width ratios. Comfortably "not significantly more than RTL".
- Non-multiple / padding cost scales with lane count `= (InW+OutW)/gcd(InW,OutW)`
  (the placement demux + per-lane shift). Inherent to arbitrary-ratio gearboxing,
  **bounded** (not the old O(W²) barrel shifter), and minimized when the folding
  optimizer pads to a width pair with a larger gcd. Guidance for the optimizer:
  prefer padding targets that raise gcd(InWidth, OutWidth).

### Measurement caveat (fixed)
An early `lut_harness` bug used `NumIn=NumOut=2` for every pair, so k:1 ratios were
silently measured as pad/crop, not exact. Fixed to choose word counts by LCM so
`mode=exact|pad|crop` is honoured. The definitive exact-vs-pad-vs-crop numbers are
in `final_correct_sweep.txt`; the plain reference (`ref_plain/`) was already exact.

Kernel dispatch (all compile-time-pruned): multiple downscale -> constant-shift
(handles pad+crop); multiple upscale no-pad -> constant-shift (plain datapath);
everything else (non-multiple, or multiple-upscale-with-pad) -> lane-granular gearbox;
equal width -> straight copy.

### Real mobilenet-v1 DWC width pairs
Extracted 55 DWCs (24 distinct) from a sized mobilenet build; all pass the

## Environment notes
- Per-node rtlsim needs `verilator`. No system verilator; `pip install verilator`
  gives v5.48, but the old `deps/pyverilator` build harness is **incompatible with
  verilator 5.x** (MULTITOP / flag differences) → `PyVerilator.build` fails for ANY
  hls node (verilator itself parses the generated DWC Verilog cleanly — the RTL is
  valid). rtlsim here needs verilator ~4.x. This is a pre-existing, kernel-independent
  tooling gap, not a DWC regression.
- cppsim for the DWC is a Python passthrough (doesn't exercise the kernel). So kernel
  correctness is validated via the C-sim testbench (`tb_dwc.cpp`), which is
  bit-accurate and broader than the pytest roundtrip — it compiles and runs the EXACT
  finn-hlslib kernel. Exposed as pytest `test_dwc_generalized_kernel_csim` (CI-able
  without verilator). PYTHONPATH needs `deps/pyverilator`.
- On a box with verilator ~4.x, run the full rtlsim matrix:
  `PATH=<verilator4>/bin:$PATH python -m pytest tests/fpgadataflow/test_fpgadataflow_dwc.py -k rtlsim`.
